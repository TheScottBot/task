# Decisions taken during the build

Decisions made on 23 September 2026 while building against `SPEC.md`, all
confirmed by the author. D numbers continue from the spec's own D3 and D4 and
answer questions raised before the build; BD numbers are build decisions made
along the way. Only D7 (with BD2 folded into the same edit) changed `SPEC.md`
itself, with the author's explicit permission; the rest are recorded here so none
is decided silently.

| id | decision | where it lives | covering tests |
|---|---|---|---|
| D5 | NAV dates: accept ISO 8601; normalise `DD-Mon-YYYY` (English abbreviation, any case) to ISO, since a written month cannot be misread; reject every numeric slash date (R5, detail `slash_date_order_unconfirmed`) and flag it in the exceptions report, because without a confirmed convention reading one is a guess. If the client confirms the slash dates are always one convention, they are normalised too; ISO at source remains the preference. This replaces the initial decision to accept unambiguous `MM/DD/YYYY`, per the author's email to the client of 23 September 2026. | `positions_feed/nav_dates.py`, one table | `tests/unit/test_nav_dates.py`, `test_r5_slash_nav_date_rejects_with_the_unconfirmed_order_named`, `test_report_flags_slash_dates_as_rejected_with_the_reason` |
| D6 | Feed bounds: 64 MiB per file, 200,000 data rows, 256 characters per field. Reaching any of them refuses the whole file; nothing is truncated. | `positions_feed/contract.py` | `tests/unit/test_feed_reader.py` |
| D7 | R5 extended to every required field in the model, applied to `SPEC.md`. | `positions_feed/validation.py` | `tests/unit/test_validation_rules.py` |
| D8 | A normalisation raises both its warn and its auto-correct finding (W4 with C3, W5 with C2), counted per rule so nothing is double-counted within a category. | `positions_feed/validation.py` | `test_w4_and_c3_...`, `test_w5_and_c2_...` |
| D9 | Exit codes: 0 for a clean pass, no file, or a file processed with rejected rows; 1 for a refused file or a store failure, and since BD7 a report or archive that could not be written; also 1 for an invalid invocation, since argparse's own exit code 2 would otherwise read as an empty file; 2 for an empty file only. | `positions_feed/cli.py` | `tests/integration/test_cli.py` |
| D10 | A header with an unknown, missing or duplicated column refuses the whole file (exit 1). | `positions_feed/feed_reader.py` | `tests/unit/test_feed_reader.py` |
| D11 | Vintage year is bounded from 1980 to the year of the run; outside that is R5. | `positions_feed/contract.py` | `test_r5_vintage_year_is_bounded_...` |
| D12 | `--database-path` stays required, with no default. A default derived from anything that can change (the drop location, the working directory, the account cron runs as) would, if it changed, quietly start a new empty store: every position inserted again and the audit trail restarted, with no error. | `positions_feed/cli.py` | `tests/integration/test_cli.py` |
| D13 | New warn rule W6: a NAV more than five times a non-zero commitment lands flagged, `nav_high_against_commitment`, detail `nav_above_5x_commitment`. The sample peaks at about 1.25x and a fund above three or four times is exceptional, so five catches a typo (a commitment of 100 against a NAV of about 2 million is roughly 20,000x) without flagging a strong real position. A zero commitment is not compared, since the ratio means nothing. Recorded here and in the code's rules table, not in `SPEC.md`, by the author's choice. | `positions_feed/contract.py`, `positions_feed/validation.py` | `test_w6_...` |
| D14 | New warn rule W7: a commitment below the one last stored for the same `source_row_id` lands flagged, `commitment_lower_than_previously_delivered`, recording both values. Any decrease counts, since a commitment is contractual and should not fall. The new value still lands (the latest delivery wins; the audit row keeps the old one). This also catches a blank commitment, defaulted to 0 by W1, wiping a known value. Checked at ingest against the store, inside the file's transaction, before the upsert. Not in `SPEC.md`, by the author's choice. | `positions_feed/ingestion.py` | `test_w7_...` |
| BD1 | The within-file duplicate rule is reported under the id `DEC-1` rather than a new R number, since the spec defines the behaviour under DEC-1 but gives it no row in the table. | `positions_feed/rules.py` | `test_dec_1_...` |
| BD2 | Also under R5, as part of the D7 edit: a negative `commitment` (the model says >= 0); a `source_row_id` with surrounding whitespace (a padded key would split one position into two); a row with the wrong number of fields. None has a safe default. | `positions_feed/validation.py` | `test_r5_unparseable_required_field_rejects`, `test_r5_row_with_wrong_number_of_fields_rejects` |
| BD3 | `status` is matched exactly, so `active` or `ACTIVE` is R4, not folded: a variant spelling of an accepted state is not silently improved (0.11). | `positions_feed/validation.py` | `test_r4_unknown_status_rejects_without_case_folding` |
| BD4 | Blank lines after the last row are ignored, being an export artefact that carries nothing; a blank line between rows is a row-shape R5 reject, since it may mark lost data. | `positions_feed/feed_reader.py` | `test_trailing_blank_lines_at_end_of_file_are_not_rows`, `test_blank_line_between_rows_is_returned_as_an_empty_row` |
| BD5 | A reject finding records the field's length, never its value, because rejected values can be personal data (0.15); a transform records before and after, and transforms never touch the personal fields. | `positions_feed/findings.py` | `test_reject_finding_carries_length_not_value`, `test_report_is_json_serialisable_and_carries_no_personal_data` |
| BD6 | Currency is checked for ISO 4217 shape (three letters), not against the list of codes: the standard library carries no code list, and 0.13 argues against a dependency for this. See `IMPLEMENTATION_DEVIATIONS.md`. | `positions_feed/validation.py` | `test_w3_non_usd_currency_lands_flagged` |
| BD7 | After its reports are written, a processed, empty or refused file is moved from the drop location into an `archive` folder beside it (or `--archive-directory` if given). The feed and its reports share one stamped stem, the feed's name plus the UTC processing moment, `stem.YYYYMMDDTHHMMSSZ`, giving `.csv`, `.report.json` and `.summary.txt`. Reports go to the archive folder by default, beside the file they describe, or to `--report-directory` if given. A full timestamp rather than the date, so a same-day re-run does not collide; if any of the three names is taken, the whole set takes `-2`, `-3` and so on, and nothing is ever overwritten, so no night's report replaces another's. A file whose reports or archive cannot be written exits 1 and stays in place, as does one whose ingest hit a store failure, for the next run to retry. | `positions_feed/archive.py`, `positions_feed/cli.py` | `tests/unit/test_archive.py`, `tests/integration/test_cli.py` |
